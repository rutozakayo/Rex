# DARKNOTE CONTROL CENTER

A Next.js administration foundation for an **existing** WhatsApp bot hosted separately on Pterodactyl. It does not create another WhatsApp connection or move the bot.

## Included in this build

- Responsive dark admin interface.
- Signed, HTTP-only admin session cookie.
- Server-side Pterodactyl Client API adapter.
- Authenticated remote directory listing and file-content viewing.
- Authenticated resource metrics endpoint.
- Neon SQL schema for server metadata, file indexes, drafts, versions, deployments, audit events and sync conflicts.
- Monaco read-only production file viewer.
- No fake server data and no production write/deploy endpoints.

## Important status

This is a **secure first integration milestone**, not the complete feature list in the original specification. Remote discovery is currently one directory at a time, not recursive. Editor is read-only. There are no upload, delete, write, restart, terminal-command, deployment or rollback actions yet. These must not be enabled until backups, conflict detection, validation, audit trails, authorization and recovery are implemented and tested.

## Run in GitHub Codespaces

Node.js 20.9+ is required.

```bash
npm install
cp .env.example .env.local
npm run dev
```

Open forwarded port 3000.

## Environment configuration

Set these in Codespaces Secrets or the deployment provider's server-side environment settings. Do not commit real secrets.

- `ADMIN_PASSWORD_HASH`: scrypt hash generated by the included setup script.
- `ADMIN_SESSION_SECRET`: random secret at least 32 characters.
- `PTERODACTYL_BASE_URL`: panel URL, e.g. `https://panel.example.com`.
- `PTERODACTYL_CLIENT_API_TOKEN`: Pterodactyl Client API token with only the required read permissions.
- `PTERODACTYL_SERVER_ID`: identifier for the existing bot server.
- `DATABASE_URL`: Neon connection string (needed for DB health/schema features).

Generate the password hash locally:

```bash
node scripts/hash-password.mjs "your-long-unique-password"
```

Paste the resulting `scrypt$...` string into the private `ADMIN_PASSWORD_HASH` environment variable. Never put the password or hash in source files or chat.

## Pterodactyl API permissions

Use a dedicated least-privilege Client API token. For this initial release, grant only server read, file read/list and resource read permissions supported by your panel version. The app uses:

- `GET /api/client/servers/{server}/files/list`
- `GET /api/client/servers/{server}/files/contents`
- `GET /api/client/servers/{server}/resources`

Confirm the panel base URL and server identifier before connecting. The server ID is not the server's display name.

## Database

Run `database/schema.sql` against your Neon database using the Neon SQL editor. The schema stores metadata only. Production files stay on Pterodactyl. Large backups must use private object storage; do not store session files or secrets in browser-accessible tables.

## Security notes

- Tokens are used only in server-side code.
- Session cookie is HTTP-only, same-site strict and expires after eight hours.
- All Pterodactyl routes require an authenticated session.
- File paths are normalized and traversal attempts are rejected.
- Read-only mode is deliberate until the full deployment safety chain exists.
- Add rate limiting, login lockout, CSRF/origin checks, MFA and a managed secret store before public production exposure.

## Connecting a Pterodactyl panel

Sign in with the website password, then complete the **Pterodactyl connection** card on the dashboard.

| Field | What it is |
| --- | --- |
| Panel URL | Full HTTPS URL, e.g. `https://panel.example.com` |
| Panel username | The exact username of the panel account that owns the API key |
| Client API key | Created in the panel under **Account → API Credentials** |

### Why an API key and not the panel password

Pterodactyl exposes no API that accepts a username and password; its Client API authenticates only with a Bearer API key. Verifying a panel password would mean scripting the panel's web login form, which is unsupported and unsafe. The key's owning account is read from `GET /api/client` and compared with the username you enter, so the connection is genuinely bound to that account — a wrong username fails verification.

### What verification proves before anything is saved

1. The URL is valid HTTPS.
2. `GET /api/client` succeeds and returns the key owner's identity.
3. That identity matches the username supplied.
4. `GET /api/client/servers` lists the servers the account can reach.
5. The Darknote/WhatsApp server is identified (auto-detected, or chosen from a list when ambiguous).
6. `GET /api/client/servers/{id}/resources` proves server read access.
7. `GET /api/client/servers/{id}/files/list` proves the `file.read` permission.

`CONNECTED` is only reported after all seven succeed. Failed verification never persists anything and returns one of: `invalid_url`, `authentication_failed`, `permission_insufficient`, `panel_unavailable`.

### Required environment variables

| Variable | Purpose |
| --- | --- |
| `ADMIN_PASSWORD_HASH` | scrypt hash from `scripts/hash-password.mjs` |
| `ADMIN_SESSION_SECRET` | 32+ random characters, signs the session JWT |
| `PANEL_ENCRYPTION_KEY` | 32+ random characters, AES-256-GCM key for the stored API key |
| `DATABASE_URL` | Neon connection string; stores connection metadata |

Generate secrets with `openssl rand -base64 48`. Website login needs only the first two; the panel is attached through the UI, not through environment variables.

`PTERODACTYL_BASE_URL`, `PTERODACTYL_CLIENT_API_TOKEN` and `PTERODACTYL_SERVER_ID` remain supported as a single-panel fallback for existing deployments.

`PANEL_STORE=memory` is a development-only override that keeps connection state in process memory. Never use it in production.
